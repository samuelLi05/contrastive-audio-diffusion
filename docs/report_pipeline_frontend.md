# Pipeline Design

The project was designed as a set of modular stages rather than one monolithic end-to-end application. The preprocessing code, training code, offline evaluation scripts, and Django demo are run separately, but they communicate through a small number of stable artifacts: waveform tensors, JSONL metadata, Hydra configuration files, and PyTorch Lightning checkpoints. This made it possible to change one part of the project, such as the conditioning method or the demo interface, without rewriting the rest of the system.

The main handoff between data preparation and model code is the standardized sample dictionary returned by the dataset loader. Each item exposes the clean waveform, noisy waveform, instrument class, numeric class id or conditioning vector, split name, and source metadata. The training and evaluation code depend on this interface rather than on the raw NSynth directory layout. This is important because the original audio files, filtered subsets, and downloaded processed dataset can all be converted into the same internal format before being passed to the model.

The training pipeline is controlled through configuration instead of hard-coded experiment settings. `train.py` uses Hydra to instantiate the selected datamodule, model wrapper, trainer options, callbacks, and logging setup. The one-hot baseline and embedding/contrastive model therefore share the same training entry point and differ mainly through configuration overrides. This design keeps the experimental comparison controlled: the data interface, checkpointing path, and trainer loop stay fixed while the conditioning path changes.

The inference pipeline reuses the same model wrapper but has a different runtime contract. Instead of launching a full training job, the Django service loads a saved config/checkpoint pair, prepares one reference waveform, constructs the matching conditioning input, runs the sampler, and writes the resulting audio and plots to the demo output directory. This keeps the web demo lightweight: it is not responsible for dataset construction or model optimization, only for packaging a single inference request and visualizing the result.

Overall, the pipeline design emphasizes reproducible handoffs. Preprocessing produces reusable tensors and metadata, training consumes that metadata and produces checkpoints, evaluation reloads checkpoints for batch comparisons, and the front-end reloads checkpoints for interactive single-sample inference. Keeping these boundaries explicit helped prevent the project from depending on hidden notebook state and made it easier to debug failures at the correct level of the system.

# Front-End

The front-end is a lightweight Django template in `realtime_demo/templates/demo/index.html`, with styling in `realtime_demo/static/demo/styles.css` and a small fetch-based controller in `realtime_demo/static/demo/app.js`. The user can provide a checkpoint, config, metadata file, and conditioning mode; upload a reference audio file or choose a dataset split and row; select the reference and target instrument classes; set the random seed, noise scale, final sampler steps, and benchmark step counts; and then run generation without leaving the browser.

On submit, the browser sends a multipart POST request to `/api/generate/`. Uploaded audio is streamed to a temporary file, while dataset references are resolved through the preprocessed metadata. The backend prepares tensors with the same inference helpers used by notebooks and scripts: audio is decoded, converted to the configured channel count, resampled, cropped or padded to the model length, and clipped to the waveform range. It then creates the noisy model input by adding seeded Gaussian noise to the clean reference, prepares either one-hot or embedding-compatible class conditioning, and runs the conditional diffusion sampler under `torch.inference_mode()`.

The response contains media URLs for the clean reference, noisy input, and generated output, plus benchmark timing records and metric summaries. The front-end updates three audio players so the user can compare the original reference, the exact noisy tensor passed to the model, and the generated/denoised result. It also plots elapsed time versus diffusion steps on a canvas, reports duration, RMS, GPU peak memory, MSE, SNR, and SNR improvement, and displays generated PNG visualizations.

The key qualitative visualization is the time-frequency PSNR heatmap. It compares the clean reference spectrogram with the generated output spectrogram and assigns low PSNR to bins where residual error is high. The interface also shows a segment-wise SNR improvement curve over time, a Mel-band before/after difference plot, the lowest-PSNR time-frequency bins, and the worst time windows by SNR gain. These outputs make the web demo more than a playback tool: it becomes a compact evaluation interface for identifying whether failures are localized to transients, sustained harmonics, low-frequency energy, high-frequency noise, or specific time windows.
